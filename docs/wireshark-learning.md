# SentinelLab — Wireshark Learning Guide

> This guide teaches you how to use Wireshark to analyze network traffic
> in the context of this project. All exercises use traffic generated by
> the local SentinelLab environment only.

---

## Why Wireshark Matters for Security Analysts

Wireshark is the world's most widely used network protocol analyzer.
Security analysts use it to:

- Investigate suspected intrusions by examining captured network traffic
- Understand exactly what data was transmitted during an attack
- Identify malicious patterns in network communication
- Verify that security controls are working correctly
- Collect forensic evidence for incident reports

If you can read a packet capture, you can see *exactly* what happened on
a network — not a log summary, the actual bytes transmitted.

---

## Core Concepts

### What Is a Packet?

A packet is a small unit of data transmitted over a network. When you
visit a website, your computer doesn't send one giant block of data.
It breaks the data into small packets, sends them individually, and
the destination reassembles them.

Think of it like mailing a book: you tear the book into pages, put each
page in a separate envelope, mail them all, and the recipient puts the
book back together.

### What Is a Frame?

A frame is the unit of data at the **Ethernet layer** (Layer 2). A packet
is encapsulated inside a frame for transmission over a local network.

The difference matters because:
- Frames travel between devices on the **same network**
- Packets travel between networks (the IP layer handles routing)

### What Is a PCAP?

A PCAP (Packet Capture) file is a recording of network traffic. It
contains every packet that passed through a network interface during
the capture period. Wireshark can open and analyze PCAP files.

## The Network Stack (Why It Matters for Packet Analysis)

Every packet has multiple layers. Wireshark shows you each layer:

```
┌────────────────────────────────────────────┐
│  APPLICATION LAYER (Layer 7)               │
│  HTTP, DNS, SMTP — the actual data/service │
├────────────────────────────────────────────┤
│  TRANSPORT LAYER (Layer 4)                 │
│  TCP or UDP — how data is delivered        │
├────────────────────────────────────────────┤
│  NETWORK LAYER (Layer 3)                   │
│  IP — addressing and routing               │
├────────────────────────────────────────────┤
│  DATA LINK LAYER (Layer 2)                 │
│  Ethernet — physical network delivery      │
└────────────────────────────────────────────┘
```

When you click on a packet in Wireshark, the packet details pane shows
all of these layers, one inside the other.

## TCP — The Transport Protocol

Most web traffic uses TCP (Transmission Control Protocol). TCP provides:

- **Reliability**: Packets are acknowledged. Lost packets are retransmitted.
- **Ordering**: Packets are numbered. Out-of-order packets are reordered.
- **Connection**: Sessions are established before data is sent.

### The TCP Three-Way Handshake

Before any data is exchanged over TCP, a connection must be established
using a three-step process:

```
Client                         Server
  │                               │
  │──── SYN ─────────────────────►│  "I want to connect"
  │                               │
  │◄─── SYN-ACK ─────────────────│  "OK, I'm ready"
  │                               │
  │──── ACK ─────────────────────►│  "Great, let's go"
  │                               │
  │       [Data exchange]         │
  │                               │
  │──── FIN ─────────────────────►│  "I'm done"
  │◄─── FIN-ACK ─────────────────│  "Acknowledged, closing"
```

In Wireshark, you can see this as:
1. A packet with the **SYN** flag set (no data)
2. A packet with the **SYN** and **ACK** flags set
3. A packet with just the **ACK** flag set
4. Then data packets begin

**Why this matters for security**: A port scanner (like Nmap) sends SYN
packets to many ports rapidly. Detecting large numbers of SYN packets
to different ports from the same source is a key indicator of a port scan.

### TCP Flags

Each TCP packet carries flags (single bits) that indicate the type of packet:

| Flag | Abbrev | Meaning |
|---|---|---|
| SYN | S | Synchronize — start a connection |
| ACK | A | Acknowledge — confirm receipt |
| FIN | F | Finish — end a connection gracefully |
| RST | R | Reset — abruptly terminate a connection |
| PSH | P | Push — send data to application immediately |
| URG | U | Urgent — high-priority data |

**Security significance of RST**: A large number of RST packets can indicate
a port scan (server rejecting connection attempts on closed ports) or
TCP session hijacking.

## IP — The Network Layer

The IP (Internet Protocol) layer handles addressing and routing.

Every IP packet contains:
- **Source IP address**: Where the packet came from
- **Destination IP address**: Where the packet is going
- **TTL (Time To Live)**: How many routers can forward this packet before it's dropped

```
Source IP: 127.0.0.1
Destination IP: 127.0.0.1
TTL: 64
Protocol: TCP (6)
```

---

## Ports — Identifying Services

A port is a number (0–65535) that identifies which application on a
computer should receive a packet.

| Port | Protocol | Service |
|---|---|---|
| 22 | TCP | SSH (secure shell) |
| 53 | UDP/TCP | DNS |
| 80 | TCP | HTTP (web) |
| 443 | TCP | HTTPS (secure web) |
| 5000 | TCP | SentinelLab vulnerable app |
| 8000 | TCP | SentinelLab API |

When you see `127.0.0.1:5000`, the `:5000` is the port. It means
"connection to the application listening on port 5000 on localhost."

## HTTP — The Application Layer

HTTP (HyperText Transfer Protocol) is the protocol browsers and APIs use.

### HTTP Request

```
POST /login HTTP/1.1
Host: localhost:5000
Content-Type: application/x-www-form-urlencoded
Content-Length: 35

username=admin&password=wrongpassword
```

Each part means:
- `POST` — the HTTP method (sending data to the server)
- `/login` — the path being requested
- `HTTP/1.1` — the protocol version
- `Host: localhost:5000` — which server to contact
- `username=admin&password=wrongpassword` — the data being sent (this is the body)

### HTTP Response

```
HTTP/1.1 401 Unauthorized
Content-Type: text/html; charset=utf-8
Content-Length: 143

<html><body>Invalid credentials</body></html>
```

- `401 Unauthorized` — the status code (means: not authenticated)
- The body contains the actual HTML response

### Common HTTP Status Codes

| Code | Meaning | Security Relevance |
|---|---|---|
| 200 | OK | Successful request |
| 301/302 | Redirect | May indicate login redirect |
| 401 | Unauthorized | Failed authentication |
| 403 | Forbidden | Access denied (auth succeeded, permission denied) |
| 404 | Not Found | Path doesn't exist |
| 500 | Server Error | Application error (may leak info) |

## DNS — Domain Name System

DNS translates domain names (e.g., `example.com`) to IP addresses.

In a PCAP, DNS traffic looks like:

```
Query:  What is the IP for "localhost"?
Answer: 127.0.0.1
```

DNS uses **UDP port 53** by default.

**Security relevance**: Attackers use DNS for command-and-control (C2)
communication (DNS tunneling). Anomalous DNS queries are an important
detection signal. In your PCAP analysis, you will extract DNS queries
as part of the network forensics pipeline.

## Using Wireshark — Practical Guide

### Starting a Capture

1. Open Wireshark
2. On Windows: Select **"Npcap Loopback Adapter"** to capture localhost traffic
3. On Linux: Select **"lo"** (loopback interface)
4. Click the blue shark fin button to start
5. Interact with the vulnerable lab app
6. Click the red square to stop
7. File → Save As → `capture.pcap`

### The Wireshark Interface

```
┌─────────────────────────────────────────────────────────┐
│  [Filter bar — type display filters here]               │
├───┬────────────┬──────┬────────┬──────┬─────────────────┤
│ # │ Time       │Source│  Dest  │Proto │ Info            │
│ 1 │ 0.000000   │127.. │ 127..  │ TCP  │ SYN             │
│ 2 │ 0.000123   │127.. │ 127..  │ TCP  │ SYN-ACK         │
│ 3 │ 0.000145   │127.. │ 127..  │ TCP  │ ACK             │
│ 4 │ 0.001000   │127.. │ 127..  │ HTTP │ POST /login     │

│  [Packet Details — expandable layers for selected packet]│

```

### Display Filters

Display filters let you see only the packets you care about.

```
# Show only HTTP traffic
http

# Show only traffic to/from a specific IP
ip.addr == 127.0.0.1

# Show only traffic on a specific port
tcp.port == 5000

# Show only SYN packets (start of connections)
tcp.flags.syn == 1

# Show only SYN packets that are NOT SYN-ACKs (port scan detection)
tcp.flags.syn == 1 and tcp.flags.ack == 0

# Show only HTTP POST requests (login attempts)
http.request.method == "POST"

# Show only failed HTTP responses (4xx or 5xx)
http.response.code >= 400

# Show only DNS queries
dns.flags.response == 0

# Combine filters with 'and', 'or', 'not'
http and ip.addr == 127.0.0.1
```

### Following a TCP Stream

"Following a stream" shows you the complete conversation between a client
and server — all the packets in order, reassembled into readable text.

1. Right-click on any HTTP packet
2. Select **"Follow" → "TCP Stream"**
3. A window opens showing the full request and response

This is how you see what data was actually transmitted — invaluable for
investigating attacks.

### Identifying Suspicious Patterns

| Pattern | What to Look For | Filter |
|---|---|---|
| Brute force | Many POST /login from same source | `http.request.method == "POST" and http.request.uri contains "login"` |
| Port scan | SYN packets to many different ports | `tcp.flags.syn==1 and tcp.flags.ack==0` |
| Path traversal | Requests containing `../` | (inspect HTTP requests manually) |
| DNS anomaly | Unusually long domain names | `dns` then look for long query names |
| Data exfiltration | Large outbound transfers | Sort by packet length, look for large payloads |

### Exporting Evidence

- **Export as PCAP**: File → Save As (preserves everything)
- **Export specific packets**: File → Export Specified Packets
- **Export as CSV**: File → Export Packet Dissections → As CSV
- **Export HTTP objects**: File → Export Objects → HTTP (saves transferred files)

## Practice Exercises

**Exercise 1 — Capture a Login Attempt**
1. Start the vulnerable lab app (`localhost:5000`)
2. Start Wireshark capturing on the loopback adapter
3. Open your browser and go to `http://localhost:5000/login`
4. Enter a wrong username and password, click Login
5. Stop the Wireshark capture
6. Apply filter: `http`
7. Find the POST request to `/login`
8. Follow the TCP stream
9. **Question**: What username and password did you type? Can you see them in the packet?

**Exercise 2 — See the Three-Way Handshake**
1. Start a new Wireshark capture
2. Open `http://localhost:5000` in your browser
3. Stop the capture
4. Apply filter: `tcp.flags.syn == 1`
5. **Question**: How many SYN packets do you see? Why might there be more than one?

**Exercise 3 — Analyze the Sample PCAP**
1. In Wireshark, go to File → Open
2. Open `sample-data/pcap/brute_force_sample.pcap`
3. Apply filter: `http.request.method == "POST"`
4. **Question**: How many login attempts are there? Do any succeed (look at the response codes)?

**Exercise 4 — Extract a Finding**
1. Open `sample-data/pcap/brute_force_sample.pcap`
2. Follow a TCP stream from a login attempt
3. Write down: source IP, destination IP, destination port, request path, response code
4. This is the information you would include in an incident report as evidence.
